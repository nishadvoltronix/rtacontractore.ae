# RTA lead delivery and privacy controls

This is a prepared, default-disabled integration for **rtacontractor.ae only**. It starts no server, worker, schedule or notification and does not read credentials on import. The working client-side Zoho form remains the sole active form provider. No live lead was submitted by this implementation or its tests.

## Current evidence and activation gaps

The existing page uses the exact `webform5653678000076526082` Zoho embed. Prior approved native testing independently matched its exact JSON acknowledgment to one CRM record. The preserved f04 tracking module handles that narrow browser acknowledgment; this service uses the separate authenticated CRM upsert API and never treats browser DOM, HTTP 200, a queued intake or a chatbot opening as CRM acceptance.

The initial 97-field audit found no user-defined unique/external ID or UTM/consent fields. Root then created and read back 19 additive non-mandatory fields (1 November Dubai): 116 fields total, the previous 97 and global Lead Status preserved. Verified `RTA_Submission_ID` is text100, unique, case-insensitive. The configuration now maps it plus `RTA_Website_Origin`, `RTA_Form_ID`, six `RTA_UTM_*` fields, `RTA_Landing_Path`, `RTA_Referrer_Host`, `RTA_GCLID`, `RTA_MSCLKID`, two consent booleans, consent timestamp/policy, technical-test flag and `RTA_Lifecycle_Stage`. The two click-ID fields are text255 and verified writable for both API create and update (`field_read_only:false`, `api_create:true`, `api_update:true`); both writability gates are true. Standard `GCLID` is read-only/create-only (`field_read_only:true`, `api_create:true`, `api_update:false`) and is deliberately excluded from retryable upserts. No private field IDs are stored here.

Global Lead Status remains unchanged. The separate new lifecycle picklist has New Lead, Qualification, Site Visit, Proposal Sent, Negotiation, Won and Lost. Activation requires all of the following, currently unverified/missing:

- The additive field map/unique key and the custom click-ID fields' create/update writability are verified and wired, but server OAuth/API region, credentials and automation behavior must still be verified. Configuration flags record an operator verification checklist, not proof of legal compliance or a lawful basis. Review actual data use, recipients and policy before activation.

## Flow and contracts

`POST /api/leads/challenge` with `{}` issues a signed, age-bounded, non-PII form challenge. The user completes an explicitly integrated server-owned form. `POST /api/leads` accepts JSON and a random UUID-v4 `Idempotency-Key`; the existing Zoho form is never intercepted. First/last name fields are explicit rather than guessed by splitting a name. The `website` input is an empty honeypot, not a customer website mapping.

Canonical input: `firstName` (optional), `lastName`, `company`, `mobile`, `email`, `requestedService`, `projectLocation`, `projectDescription`, optional `projectName`, `website: ''`, `challenge`, `consent: {analytics, advertising, policyVersion, known, recordedAt?}`, optional bounded `attribution`. The server supplies source origin, server-form identity, technical-test flag and time. Unknown consent is recorded as not-recorded, omitting CRM booleans/timestamp rather than fabricating explicit denial. A known choice needs a valid reported timestamp; this representation is not legal proof of consent. Unknown keys, oversized content, controls, obvious spam, invalid contacts, arbitrary referrer/URL fields and click IDs without advertising consent are rejected. Challenge age/honeypot/rate checks reduce abuse; they are not CAPTCHA or a guarantee against bots.

The durable encrypted queue returns **202 queued, accepted:false**. This is not a conversion. `POST /api/leads/status` with `{}` and the same key returns only status/accepted/duplicate, without contact fields, CRM IDs or tokens. `duplicate:true` marks a fresh-key alias of the same recent enquiry; the client does not count it as another conversion after reload/resubmission. `tick()` delivers via a verified unique-field Zoho upsert. Only record-level `SUCCESS`/`success` with an actual insert/update and record ID promotes the entry to accepted. HTTP status alone is insufficient.

Same-key changed payload returns 409. Identical recent enquiries can alias to one record within the reviewed dedupe window; project name and the server-owned source/form/technical-test context are part of enquiry identity, while campaign and consent metadata are not. Retries retain the same key/body/external ID. Ambiguous delivery, including a malformed or unrecognized 2xx provider receipt after a possibly accepted write, is retried only for an adapter with verified external-ID idempotence, at most three attempts with delay. Unsafe uncertainty becomes reconciliation-required. A crash in sending state follows the same rule. HUB delivery happens after CRM confirmation and never resubmits CRM on HUB failure. No browser-to-Zoho fallback happens after a possibly sent server request.

`createLeadRuntime(config, options)` composes the handler/store/adapters but never binds a port. The hosting application must mount its handler and explicitly schedule bounded `tick()` calls after deployment approval. Inject `privateStateDirectory`, `key`, `getAccessToken`, approved `resolveClientAddress`, and the verified HUB/lifecycle contracts. Do not trust forwarded headers without a verified proxy boundary. Single-writer lock failures require an operator to establish the former process stopped; no automatic stale-lock deletion exists.

`http-entry.mjs` supplies a usable opt-in mount for the current static-hosting architecture. Importing it creates no listener. Running it without `--enable` prints Disabled and exits without loading private configuration. After all runtime/credential/policy gates and deployment approval, an operator can supply an **absolute private module outside the checkout/public root** that exports `leadConfig` and `runtimeOptions`, then explicitly invoke:

```sh
node server/lead-service/http-entry.mjs --enable --port=41001 --runtime-config="$RTA_PRIVATE_RUNTIME_MODULE"
```

The port is an explicit operator choice. Only literal loopback `127.0.0.1` (default) or `::1` is accepted. The module validates the encrypted state location outside the checkout/public root, limits connections and request/header time, and starts a bounded worker interval only after `listen()`. The local `/healthz` reports readiness/worker-loop outcome without records; `health()` returns aggregate queue/failure counts and pending age. Neither is proof of a successful provider write. The existing Nginx mount, HTTPS/proxy trust and process-manager installation require separate verified deployment configuration; none was changed or started here.

The AES-256-GCM journal writes a private temporary file, fsyncs, atomically renames and fsyncs the directory on Linux. Its dedicated state directory must be separate from the checkout/public root and their ancestors. Only a new leaf directory is created, with mode 0700; existing parents are never created or chmodded. An existing Linux directory must already be owned by the service user with mode 0700 and contain only the store's reserved files. Keep runtime configuration and keys in separate private locations, not inside this directory. Any persistence error poisons the process store until reopen/reconciliation. Local Windows tests prove authenticated encryption and reopen behavior, not the production Linux filesystem/durability boundary or POSIX permissions branch. Back up encrypted state and its key through separate protected procedures. Do not replace the key in place: existing ciphertext and idempotency HMACs depend on it, so rotation needs a reviewed drain/retention/migration procedure. Purging is explicit and removes entries plus challenge indexes; no retention schedule is installed.

`purgeExpired()` reports `removed`, `deferred` and `deferredEntries`. During an active CRM/HUB batch it returns `deferred:true`, `removed:0`, an unknown count (`null`) and `reason:delivery_in_progress`; nothing is claimed erased. An expired sending row left after a crash is also retained, with an observed deferred count and `reason:sending_entries_require_recovery`. The approved retention runner must act on this result: wait for the active batch or establish recovery/reconciliation, then invoke an explicit follow-up purge and verify its result. Deferral is not completion of retention. Queue health exposes sending counts and pending age; configure an approved overdue-retention/failure escalation before activation so a deferred purge cannot silently become indefinite. Resolve pending outbox/reconciliation obligations under the approved policy before erasing their journal evidence. No follow-up schedule, notification or provider request is created automatically.

Lifecycle processing is an internal function, not an unauthenticated public webhook. An injected provider verifier must establish authenticity/replay protection and an existing accepted CRM record before an allowlisted stage is recorded. Outbox events contain only event/stage names; no active analytics transport is installed. Client success emission is separately disabled to prevent duplicate server/client conversion delivery. Agree one event owner before enabling a transport.

## Website consent and attribution

`website/marketing.config.mjs` and the new controller are disabled. The preserved f04 GTM loader therefore still works as before; the inactive controller makes no claim to gate current tracking. It exposes an inert `window.RTAMarketing` API and does not store a new choice, start providers, bind a form or send a request while disabled.

Future coordinated activation requires all of `enabled`, `consent.enabled`, `integrationReady`, `granularTagGatesVerified` and the exact verified container version. The build must omit its previous GTM head/noscript loaders in this mode. The controller then queues denied defaults before its sole GTM bootstrap, presents independent analytics/advertising choices, and loads the container when at least one purpose is explicitly granted. Every vendor base, event, conversion and custom tag must be purpose-gated; gating only initialization tags is insufficient. The current integration flags remain false until root proves that container configuration.

Exact data-layer contract:

```js
{ event: 'rta_consent_update',
  rta_consent_analytics: 'granted', // or denied
  rta_consent_advertising: 'denied', // or granted
  rta_consent_policy_version: 1 }
// Then, once per granted purpose per page:
{ event: 'rta_consent_analytics_granted' }
{ event: 'rta_consent_advertising_granted' }
```

A GTM consent template must consume the update through its synchronous `setDefaultConsentState`/`updateConsentState` APIs before grant events. Source-side queued gtag commands alone do not establish those GTM timings. Google `ad_user_data`/`ad_personalization` remain denied in this two-choice controller. UET has a separate consent queue; root must verify delayed-loading initial consent inheritance. Clarity uses exact `consentv2` keys `analytics_Storage` and `ad_Storage`; its project cookie/consent settings require separate owner verification.

The controller persists only the actual choice, schema/policy version and timestamp. Missing, malformed, future, expired or unavailable choices fail closed. Withdrawal sends denied updates, clears owned attribution, persists denial and reloads the document. Consent APIs do not generally unload active listeners or reverse previous transfers; no instantaneous universal network-stop or legal-compliance claim is made.

Before loading tags, reviewed static paths and consented opaque click IDs are retained; UTM values survive into vendor URLs only if exactly in the configuration's verified-public campaign allowlist. Other query values and unknown fragments are removed. Valid existing anchor targets are preserved. `rta_page_location` is sanitized for coordinated GTM use. Unknown paths fail to load. Bounded unapproved UTM text can remain only in first-party/server lead attribution, not analytics URLs. Campaign links must never carry personal information. Attribution storage requires a corresponding explicit choice; it retains the last non-direct touch without refreshing its age on internal navigation, includes only allowlisted referrer hosts rather than full URLs, and labels AI referral classification as heuristic.

The controller governs this GTM container only. Existing Zoho, SalesIQ and AI widgets outside GTM require their own reviewed purpose/activation behavior; this implementation does not silently change their settings. The new public CTA hooks emit only `request_quote`, `service_enquiry` or `company_profile_download` after a purpose grant, never arbitrary labels, addresses or URL values. These are click intents: opening a profile PDF is not proof of a completed download or lead. Existing f04 contact/assistant events retain their existing owner.
